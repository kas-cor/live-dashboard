🔴 Critical (5)

1. Отсутствие аутентификации на всех API-эндпоинтах — backend.py:27, backend.py:1022-1053
Проблема: CORS разрешён для всех origin (allow_origins=[""]), все CRUD-эндпоинты конфигурации (/api/config/) открыты без какой-либо аутентификации. Любой, кто может достучаться до порта 9090 (или 3003 через nginx), может читать и изменять конфигурацию виджетов, включая список мониторимых сайтов и пороги алертов. Эндпоинт POST /api/alert позволяет отправлять произвольные вебхуки.
Решение: Добавить API-ключ (из env) и проверять его в middleware или зависимости FastAPI. Как минимум — закрыть PUT/POST/DELETE на /api/config/* и POST /api/alert.

2. Потенциальная command injection в эндпоинте логов — backend.py:548-555
Проблема: Параметр services из query-строки напрямую подставляется в shell-команду через bash -c. Строка 553: f"journalctl --directory=/host/log/journal _SYSTEMD_USER_UNIT={u_svc}.service ..." — значение u_svc извлечено из пользовательского ввода через regex, но не санитизировано. Злоумышленник может передать services=[user]$(malicious command).
Решение: Валидировать services по белому списку допустимых имён systemd-юнитов (только [a-zA-Z0-9_\-\.@]+). Не использовать bash -c — передавать аргументы списком в subprocess.run().

3. Жёстко захардкоженные геоданные и fallback-данные — backend.py:633, backend.py:641, backend.py:651
Проблема: Эндпоинт /api/weather полностью игнорирует переменные окружения WEATHER_LAT, WEATHER_LON, WEATHER_CITY из .env.sample и использует жёстко зашитые координаты Москвы (55.7558, 37.6173) и city="Moscow". Эндпоинты /api/docker (строки 465-467) и /api/todo (строки 586-593) возвращают жёстко захардкоженные демо-данные при ошибке, что маскирует реальные сбои.
Решение: Использовать переменные окружения в /api/weather. Для fallback-данных — возвращать пустые структуры с флагом error, а не подставные данные.

4. Гонка данных (race condition) в AlertService._increment_consecutive — backend.py:129-189
Проблема: Метод читает строку из БД, инкрементирует в Python, и пишет обратно — без блокировки. При concurrent-запросах (например, два виджета одновременно проверяют метрики одного сервера) возможна потеря инкрементов: оба прочитают consecutive_hits=2, оба запишут 3 вместо 4. SQLite в режиме WAL допускает concurrent readers, но не защищает от lost updates.
Решение: Использовать атомарный UPDATE ... SET consecutive_hits = consecutive_hits + 1 и RETURNING (SQLite 3.35+) или BEGIN IMMEDIATE транзакцию.

5. asyncio.get_event_loop() в синхронных эндпоинтах — backend.py:388, 442, 801, 824, 927
Проблема: Вызов asyncio.get_event_loop() из синхронной функции (def, не async def) в разных потоках или при определённых настройках event loop может вернуть разные loop'ы или выбросить RuntimeError. Фоновые задачи (create_task) создаются без отслеживания — если задача упадёт, исключение будет потеряно.
Решение: Перевести эндпоинты на async def и использовать asyncio.create_task() с asyncio.TaskGroup для structured concurrency. Или вынести отправку вебхуков в фоновый поток через loop.call_soon_threadsafe.



⚠️ Warnings (10)

1. Множественные голые except: — backend.py:337, 344, 348, 354, 358, 361, 369, 374, 379, 562, 585, 670
Проблема: Голые except: (без указания типа исключения) ловят всё, включая KeyboardInterrupt и SystemExit, и молча проглатывают ошибки. Это антипаттерн, который скрывает баги.
Решение: Заменить на except (FileNotFoundError, ValueError, subprocess.CalledProcessError) as e: с логированием logger.warning(...).

2. get_db() создаёт новое соединение на каждый вызов — backend.py:32-69
Проблема: Каждый вызов get_db() открывает новое соединение с SQLite, создаёт таблицы (CREATE TABLE IF NOT EXISTS), выполняет миграции, и закрывает. В одном запросе /api/sysinfo это происходит 3+ раза (get_widget_config_dict → get_db, alert_service._get_row → get_db, alert_service._increment_consecutive → get_db). Это избыточно и создаёт фрагментацию.
Решение: Использовать sqlite3.connect с check_same_thread=False и кэшировать соединение в threading.local или использовать contextlib.contextmanager. Миграции выполнять один раз при старте.

3. import re и import('re') внутри цикла — backend.py:500, 508
Проблема: В эндпоинте /api/tailscale import re вызывается внутри цикла по пирам (строка 500), а на строке 508 — import('re'). Импорт внутри цикла — лишний оверхед. import — неидиоматично.
Решение: Вынести import re наверх файла (он уже импортирован на строке 6!).

4. Дублирующиеся импорты — backend.py:10, 978, 979
Проблема: from pydantic import BaseModel на строках 10 и 978. from typing import List на строке 979 (и Optional на 11). Мёртвый код.
Решение: Удалить дубликаты.

5. Модульные глобальные кэши не потокобезопасны — backend.py:674, 850
Проблема: SERVER_CACHE и SITE_CACHE — модульные словари, мутируемые из разных запросов. При использовании нескольких workers (uvicorn с --workers N) каждый процесс имеет свою копию, но в рамках одного процесса concurrent-запросы могут читать/писать кэш без синхронизации.
Решение: Использовать asyncio.Lock для асинхронных эндпоинтов или threading.Lock для sync.

6. entrypoint.sh не обрабатывает падение процессов — entrypoint.sh:9, 20
Проблема: wait без -n ждёт завершения всех фоновых процессов. Если nginx упадёт, backend продолжит работать, но wait не вернётся, пока жив backend. Если backend упадёт — аналогично. Нет рестарта.
Решение: Использовать wait -n (bash 4.3+) в цикле с проверкой кодов возврата и рестартом упавшего процесса. Или использовать supervisord.

7. docker-compose.dashboard.yml с network_mode: host — docker-compose.dashboard.yml:6
Проблема: Режим host обходит сетевую изоляцию Docker. Контейнер имеет прямой доступ ко всем сетевым интерфейсам хоста. В сочетании с отсутствием аутентификации на бэкенде это увеличивает поверхность атаки.
Решение: Если нужен только проброс конкретного порта, использовать ports с явным binding'ом на Tailscale IP.

8. data/dashboard.db и pycache/ закоммичены в репозиторий
Проблема: Файл data/dashboard.db (SQLite база) и pycache/backend.cpython-312.pyc присутствуют в репозитории. .gitignore содержит data/, но файл уже был добавлен до gitignore. База данных может содержать конфигурацию и не должна быть в VCS.
Решение: git rm --cached data/dashboard.db pycache/ и убедиться, что .gitignore применяется.

9. background_alert_loop вызывает собственные HTTP-эндпоинты — backend.py:1066-1138
Проблема: Фоновый цикл алертов делает HTTP-запросы к http://127.0.0.1:{PORT}/api/sysinfo и другим эндпоинтам вместо вызова внутренних функций напрямую. Это создаёт лишнюю нагрузку, зависимость от network stack, и может привести к deadlock при высокой нагрузке.
Решение: Вызывать функции сбора данных напрямую (вынести логику из эндпоинтов в отдельные функции).

10. SERVERS_CONFIG загружается только при старте — backend.py:771-775
Проблема: Конфигурация серверов читается из SERVERS_CONFIG (env) один раз при импорте модуля. Изменение переменной окружения или добавление сервера через API не подхватится без рестарта.
Решение: Читать SERVERS_CONFIG в эндпоинте или перезагружать периодически.



💡 Suggestions (7)

1. Перевести эндпоинты на async def. Все эндпоинты сейчас синхронные (def), но выполняют I/O (чтение файлов, subprocess, HTTP-запросы). FastAPI может исполнять sync-эндпоинты в threadpool, но это менее эффективно. Рекомендация: использовать async def + aiofiles / asyncio.create_subprocess_exec.

2. Добавить health check. Эндпоинт /api/health с проверкой доступности Docker socket, Tailscale socket, БД. Полезно для Docker healthcheck и мониторинга.

3. Структурировать ответы через Pydantic модели. Сейчас все эндпоинты возвращают dict. Явные модели ответа улучшат документацию (OpenAPI) и валидацию.

4. Добавить rate limiting. Особенно для эндпоинтов, делающих subprocess-вызовы (/api/docker, /api/tailscale, /api/logs). Библиотека slowapi интегрируется с FastAPI.

5. Вынести urllib.request наверх. Импорты внутри функций (weather, crypto, check_site) работают, но неидиоматичны. Лучше импортировать наверху и использовать httpx (уже установлен) вместо urllib для консистентности.

6. Добавить таймауты на все subprocess-вызовы. subprocess.check_output([...]) в ssh_collect имеет timeout=10, но docker и tailscale — нет. При зависании Docker daemon запрос повиснет навсегда.

7. Использовать shlex.quote для shell-аргументов. В эндпоинте логов значения подставляются в shell-команду без экранирования. Даже после валидации, shlex.quote — дополнительный уровень защиты.
